# Циклы и суперсеты: модель IOS-04

Пользователь поручил продолжать согласованный бэклог самостоятельно, без дополнительных вопросов. Этот контракт фиксирует консервативный путь: один текущий цикл, отдельные снимки календаря и тренировки, никаких библиотек именованных программ. Серверная модель — первый этап IOS-04; готовность iOS отмечается отдельно в его плане.

## Независимые снимки

Текущий повторяющийся шаблон, цикл, созданная календарная неделя, активная тренировка и завершённая история — самостоятельные ресурсы. Изменение или удаление цикла не переписывает ни один из остальных ресурсов. Сервер не создаёт недели по расписанию и не измеряет время тренировки. После начала тренировка сохраняет свой снимок даже при изменении календаря.

Цикл — 2–12 последовательных календарных недель, начало в понедельник, явный IANA timezone, необязательное повторение всей последовательности. Каждая фаза имеет UUID и ровно семь дней с существующими снимками `PlannedExercise`. Пропуск занятия не сдвигает недели и не повышает нагрузку. Автоматическое планирование на клиенте должно сначала показывать предпросмотр; фактический запас повторений им не заполняется. Технические пределы подходов и отдыха не являются тренировочными рекомендациями.

## API цикла

`GET /v1/cycle` требует `schedule:read`; `PUT /v1/cycle` — `schedule:write`. Владелец — только subject проверенного токена. Хранение — ключ `cycle` в существующем JSON storage, без SQL-миграции. Ответ: `{revision,document}`. PUT: `{expectedRevision,requestID,document}` с прежними CAS, owner lock и idempotency receipts. Начальное состояние: `{revision:0,document:{version:1,plan:null}}`.

Документ: `{version:1,plan:{id,startWeek,timezone,repeats,weeks:[{id,days:[]}]}}`. Даты остаются в пределах 1900–9999, включая конец последней недели. Удаление — явный `{version:1,plan:null}` с актуальной revision и новым requestID; revision сохраняется. Повтор старого успешного запроса возвращает старый receipt, не восстанавливая удалённый цикл. Клиент не должен понижать свою revision по такому ответу.

Формат будущей версии возвращает `upgrade_required`; повреждённый сохранённый документ — `invalid_resource`. Они не заменяются пустыми данными. Действуют строгий JSON и общий предел тела 2 MiB. Настройки OAuth и Android не меняются.

## Контекст занятия

`TrainingDay`, `ScheduledWorkout` и `WorkoutSession` могут содержать `context`:

```json
{
  "variant": "A",
  "loadType": "heavy",
  "difficulty": "hard",
  "cycle": {
    "cycleID": "00000000-0000-4000-8000-000000000001",
    "weekID": "00000000-0000-4000-8000-000000000002",
    "weekNumber": 1
  }
}
```

`variant`: пусто либо `A/B/C`; `loadType`: `regular/heavy/light/deload`; `difficulty`: `unspecified/easy/moderate/hard`. Это плановые метки, независимые от фактического RIR. Ссылка `cycle` допустима только в созданной неделе и тренировке; в повторяющемся шаблоне и исходных днях цикла запрещена. Историческая ссылка не требует существования текущего цикла: удаление плана не уничтожает происхождение снимка.

## Версия структуры и старые клиенты

У `Template`, `TemplateWrite`, `TrainingWeek`, `WeekWrite` и `WorkoutSession` есть необязательный `structureVersion`. Отсутствие/0 — старый формат, 1 — поддержка контекста и суперсетов. Новые поля требуют 1; неизвестная большая версия отклоняется с `upgrade_required`. Сериализация старого формата не добавляет новые поля, сохраняя смысл и хеш прежних запросов.

После первой записи версии 1 обратный переход к 0 запрещён, даже если пользователь явно очистил весь контекст и группы. Это сохраняемый маркер поддержки формата: старый клиент не может стереть новые данные полным PUT, удалением всех занятий или окончанием той же активной тренировки. Узкие команды переноса, отдыха и пропуска сохраняют структуру. Явное обнуление всей активной тренировки по прежнему контракту остаётся возможным для отмены или после подтверждённой записи истории. Сервер выпускается раньше клиента.

## Плановый суперсет

День шаблона/цикла и календарное занятие могут содержать `supersets`:

```json
{
  "id": "00000000-0000-4000-8000-000000000003",
  "exerciseIDs": [
    "00000000-0000-4000-8000-000000000004",
    "00000000-0000-4000-8000-000000000005"
  ],
  "restSeconds": 90
}
```

Группа связывает 2–4 карточки `PlannedExercise.id` того же дня в явном порядке. Одна карточка принадлежит максимум одной группе; число подходов у членов группы одинаково. Всего до 25 групп и прежних 50 карточек на день. Отдых между кругами — 0–600 секунд. Отдых отдельных упражнений сохраняется для самостоятельных подходов, но внутри круга клиент не запускает его автоматически.

## Суперсет выполняемой тренировки

Тренировка хранит `supersets` из `{id,exerciseIDs,restSeconds,isClosed,rounds}`. `exerciseIDs` — упорядоченные UUID физических карточек `SessionExercise.id` для оставшегося выполнения. Круг: `{id,ordinal,setIDs}`; в `setIDs` ровно один слот на члена группы. Каждый слот — UUID конкретного `LoggedSet` либо null. Существующие значения и RIR остаются в самих подходах.

До 50 записей групп и до 600 кругов в группе; ordinal возрастает от 1 до 600. Один подход нельзя включить дважды, круг содержит разные физические карточки, пустые круги удаляются. Незавершённая ссылка должна принадлежать текущему члену соответствующего слота. Закрытая группа содержит только выполненные ссылки; остальные подходы остаются в карточках со своими черновиками.

При замене карточка с прежними результатами и заметкой сохраняется, невыполненное помечается пропущенным, новая карточка получает новые UUID и пустые подходы. Только будущие ссылки группы перенаправляются на новые подходы. Уже выполненные ссылки сохраняют исходную физическую карточку, упражнение, группу, UUID круга, ordinal и позицию. Изменение этих связей или удаление группы с выполненными ссылками возвращает 409 `superset_conflict`, в том числе при завершении офлайн через history. Изменять фактические результаты в активной тренировке можно по прежнему контракту; завершённая история неизменна.

Роспуск группы сохраняет выполненные связи в закрытой записи и снимает только невыполненные ссылки. Пропуск, после которого в открытой группе остаётся меньше двух непропущенных участников, делает то же самое; группа без выполненных связей удаляется. Снятие пропуска не открывает её автоматически. Переупорядочивание карточек не меняет порядок слотов группы. Создание новых кругов должно соблюдать прежние 1–12 подходов на физическую карточку. Отдельно добавленный подход не включается в круг неявно.

## Проверки и границы

Доменные тесты покрывают границы цикла, некорректные группы, ссылки и слоты, замену/закрытие, защиту источника выполненного результата, старый JSON и отсутствие совместного изменяемого объекта у ответа/запроса. HTTP-тесты проверяют identity/scope и строгий JSON. Интеграционные PostgreSQL-тесты проверяют owner/CAS, конкурентную запись, старый receipt после удаления, независимость снимков, узкие команды и защиту history внутри существующей транзакции. Они запускаются на отдельной тестовой БД в CI; локальная production-БД для проверки не используется.

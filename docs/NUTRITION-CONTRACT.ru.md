# Питание: предлагаемый контракт IOS-06/07

Статус: проект для согласования перед API и синхронизируемым UI. Не описывает уже выпущенное поведение. Тренировки, протеиновые отметки и Android не меняются.

## Владение и хранение

Используем существующие `service.Resource`, `Repository.Get/Update` и PostgreSQL `training_resources`. Новая SQL-таблица и универсальный CRUD не нужны. JSON питания имеет собственную версию формата `version: 1`; неподдерживаемая версия отклоняется, а не очищается. Transport разбирает запрос, service проверяет предметные правила, repository обеспечивает owner lock, CAS, idempotency и audit.

Все личные маршруты требуют прежний access token. Owner берётся только из проверенного subject, никогда из тела запроса. Каталог продуктов и авторских рецептов публичный; дневник, цели, свои рецепты и избранное приватные. Ответы личных маршрутов — `Cache-Control: no-store`.

## Ресурсы и маршруты

| Маршрут | Содержимое | Ключ ресурса |
|---|---|---|
| `GET /v1/nutrition/catalog` | Версия, продукты, исходные КБЖУ, рецепты и источники | Встроенный каталог backend |
| `GET/PUT /v1/nutrition/days/{YYYY-MM-DD}` | Приёмы пищи, записи и снимок цели дня | `nutrition/day/{date}` |
| `GET/PUT /v1/nutrition/goals` | Ручные цели с датой начала действия | `nutrition/goals` |
| `GET/PUT /v1/nutrition/recipes` | Собственные рецепты пользователя | `nutrition/recipes` |
| `GET/PUT /v1/nutrition/preferences` | ID избранных продуктов/рецептов | `nutrition/preferences` |

GET возвращает `{revision, document}`; отсутствующий ресурс — revision 0 и пустой документ текущей версии. PUT: `{expectedRevision, requestID, document}`. `requestID` — UUID, тот же повтор возвращает прежний результат, другой payload с тем же ID — `idempotency_conflict`; устаревшая revision — 409 `revision_conflict`. Проверка версии и данных выполняется до записи. Неизвестные поля write-контракта отклоняются, чтобы новый формат не терял данные в старом клиенте.

PUT заменяет только один названный ресурс целиком. Дневник хранится по дням: редактирование завтрака не переписывает другие даты. Удаление записи/рецепта — явное действие пользователя, после которого сохраняется новый документ с CAS. Пустой день сохраняет revision, поэтому запоздалый старый запрос не восстанавливает удалённые записи. Экспорт получает актуальные документы за выбранные даты; клиент не полагается на неполную пагинацию истории тренировок.

## Продукты и расчёт

Продукт каталога содержит стабильный ID, русское название, исходное название, состояние (сырой/готовый и конкретный способ обработки), исходные FDC ID, тип/версию выгрузки, ссылку и КБЖУ на 100 г съедобной части. Источник — USDA FoodData Central, CC0; перевод и сопоставление выполняются по точным ID. Значения энергии и граммов берутся из исходных nutrient ID и единиц; недостающий нутриент не становится нулём. Не используем похожее название как подтверждение одинакового состава.

Вычисляем четыре значения отдельно: `на100г × масса / 100`. Энергию не подменяем формулой 4/9/4, если источник содержит собственное значение. Все входы и промежуточные результаты конечные и неотрицательные; округление применяется только при отображении. Масса — граммы съедобной части, без упаковки, костей и скорлупы. Для масла/соусов учитываются только явно внесённые ингредиенты.

Своя запись может содержать вручную введённые КБЖУ на 100 г; UI помечает источник «Введено вручную». Это не меняет общий каталог. Неизвестные КБЖУ нельзя использовать для готового расчёта без явного ручного заполнения.

## Рецепт и порции

Рецепт содержит ID, название, категорию, ингредиенты с массой и снимком состава, шаги, время, число порций и **готовую массу блюда**. При создании готовую массу задаёт пользователь; в авторском каталоге она указана как ориентир, который можно заменить фактически взвешенной массой.

КБЖУ всего блюда — сумма ингредиентов. На порцию — сумма / число порций; на 100 г готового блюда — сумма × 100 / готовая масса. Уваривание и впитывание воды меняют массу, а не автоматически исходные нутриенты. Рецепты с удалением бульона/жира требуют соответствующих данных; простой пересчёт массы не изображает точный анализ таких блюд.

Число порций может быть дробным. Действия «Количество порций» и «Съедено граммов» явно различаются. Смена количества ингредиентов не заменяет готовую массу незаметно: перед расчётом на 100 г требуется подтвердить массу нового приготовления.

## День и снимки

День содержит календарную дату, timezone, записи приёмов пищи и снимок действовавшей цели. Запись: UUID, тип приёма (`breakfast/lunch/dinner/snack`), название, съеденная масса в граммах, снимок КБЖУ на 100 г, происхождение (catalog product / catalog recipe / own recipe / manual), версия и исходный ID при наличии. Итоги выводятся из снимков; клиентские суммы сервер перепроверяет, а не принимает как достоверные.

Редактирование каталога или собственного рецепта не меняет записанные дни. Пользователь может явно заменить отдельную запись актуальным составом; это новое изменение дня с CAS. Отметки «протеин утром/вечером» не создают еду или калории.

Цель — ручные положительные kcal и неотрицательные граммы Б/Ж/У с датой начала действия. Новая цель применяется к новым дням с этой даты. Уже созданные дни сохраняют прежний снимок. Не навязываем медицинские нормы и не выдаём ручные цели за персональную рекомендацию. Автоматический расчёт суточной нормы требует отдельного выбора формулы и исходных данных.

## Границы ввода

Дата — валидный ISO день, timezone — существующий IANA ID. UUID уникальны внутри документа. До 100 записей в день, 100 собственных рецептов, 50 ингредиентов и 30 шагов в рецепте, 500 избранных ID и 100 изменений целей. Текстовые названия — 1–200 символов, шаг — 1–2000. Масса одной записи/ингредиента/блюда — `(0, 100000]` г, порции — `(0, 1000]`. На 100 г: энергия 0–1000 kcal; каждый макронутриент 0–100 г; сумма Б/Ж/У не больше 100 г с допуском 1 г на округление источника. Ноль допустим (например, вода), отрицательные, NaN, infinity и переполнение — нет.

Ручная цель: энергия `(0, 20000]` kcal и каждый макронутриент 0–3000 г. Это технические границы ввода, а не рекомендуемые нормы. Несоответствие энергии и 4/9/4 не исправляется молча: UI показывает введённые значения с источником.

## iOS, офлайн и конфликты

Личный архив питания хранится внутри текущего `AccountWorkspaces`, отдельно от тренировочного файла. Изменение формата требует резервной копии; повреждённый/неизвестный файл не заменяется пустым. Гость работает офлайн. Принятие гостевых данных сохраняет существующее правило нового гостевого каталога и не объединяет разные аккаунты.

Изменение дня, цели, рецептов или избранного атомарно сохраняет локальный документ и pending write. У незавершённого запроса сохраняются точные requestID, expectedRevision и payload; повтор после сбоя идентичен. При 409 сохраняется закрытая локальная копия обеих сторон, пользователь выбирает серверную или свою версию перед новой записью с актуальной revision. Автоматическое слияние граммов, целей или удалений запрещено.

При смене аккаунта пересоздаются store/sync/UI; запоздалые ответы не применяются к другому workspace. Выход сохраняет архив владельца, открывая гостевой. Даты дневника и цели используют сохранённый timezone, без переноса еды между днями при поездке.

## Приёмка реализации

Проверить конечные числа, нулевой продукт, граммы/порции/готовую массу, округление и неподменённую энергию; неизменность снимков после редактирования рецепта/цели; owner isolation, revision conflict, точный idempotent retry, удаление и запоздалый запрос; восстановление pending writes, повреждённый файл, миграцию, гостя и смену аккаунта. PostgreSQL — только отдельная одноразовая БД. UI — один достаточный прогон нового сценария только на iPhone 15.
